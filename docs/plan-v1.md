# dehydrater v1 开发计划

v0.1 已完成（见 [v0.1.md](v0.1.md)）。本计划按优先级列出到 v1.0 要做的事，每项说明做法、对现有代码的影响和完成标准。总体架构与设计原则见 [design.md](design.md)，其中"只用音频和 PDF，不识别视频画面"继续适用。尚未确认的问题都标为 **【待确认】**，并汇总在文末。

**开发方式**：在 `dev` 分支开发，`main` 只合入可用版本；版本号由你在 `pyproject.toml` 中手动维护并打标签。每个里程碑结束时更新 README 与 design.md，并在真实课程上跑一遍。

## 总览

| 里程碑 | 内容 | 依赖 |
| --- | --- | --- |

## M1 PDF 页面截图插入笔记 ✔ 方案已确认

**目标**：`notes.md` 中在讲到某张图表的地方插入对应课件页的截图，图片存放在 `<输出目录>/images/`。

**做法**：

1. **截图粒度：整页**。实测测试课件几乎每页都有来自模板的线条和校徽图片，按图形区域裁剪会把装饰也当成图表，误判多；而幻灯片本身就是一页一个视觉单元，整页截图最稳。用 PyMuPDF 已有的 `page.get_pixmap(dpi=…)` 渲染，默认 150 DPI（单页约 100–200KB），不需要新依赖。
2. **哪些页值得插图**：由程序先给每页打标记，再由模型决定插在哪里。
   - 程序：用 PyMuPDF 统计每页的图片面积、矢量图形数量和文字量，排除"几乎只有文字"的页，标记其余为"含图"。阈值在测试课件上调。
   - 模型：撰写笔记时，提示词告诉它哪些页含图；它在合适的位置写 `[[图:12]]`（全局页码）。程序校验页码属于本章且含图，替换为 `![调度.pdf 第 12 页](images/p012.png)`，与现有的 `[@段落]` 引用替换是同一套机制。
3. **只渲染被引用的页**，不为整份课件生成图片。渲染放在新阶段 `render_figures`（`write_notes` 之后，`render_notes` 之前），图片作为产物登记进缓存；换课件或改 DPI 时自动重做。
4. 图片路径用相对路径，`notes.md` 和 `images/` 一起移动后仍能显示。

**开源项目**：PyMuPDF 自带渲染就够用。将来若要"裁剪出图表"，可评估 `pymupdf4llm`（同一作者，`write_images=True` 可按版面提取图片）；Docling 等基于版面模型的方案需要在本地跑模型，不采用。

**完成标准**：真实课程的 `notes.md` 中，图表类知识点（调度甘特图、状态转换图等）旁有对应截图；纯文字页不被插图；在 Typora、Obsidian、VS Code 预览中显示正常。

**以后可能调整**：是否需要从整页截图改为裁剪图表区域，视实际使用效果再定。

## M2 长录音切段；一节课多个录音文件

### M2a 长录音切段

**目标**：任意长度的录音都能识别，时间戳在各段之间累加，用户看不到切段的痕迹。

**做法**：

1. 语音识别 adapter 声明自己的上限（单次时长、单次大小）；用户也可以用 `DEHYDRATER_TRANSCRIBE_MAX_MINUTES` 设定。超过上限才切段，不超过就和现在一样整段提交。
2. 切点选在静音处：解码出 PCM 后用 numpy 计算短时能量，在目标切点前后一分钟内找能量最低的位置。约 30 行，不引入 VAD 模型。
3. 各段并发识别（限制并发数），每段的时间加上该段的起始偏移后拼接。每段的识别结果单独缓存，失败后只重识别失败的段。
4. 日志记录每段的起止时间和切点位置。

**【待确认】火山标准版的单次时长上限**：由你实测后告知。在此之前，火山 adapter 默认不切段，只有用户设置了 `DEHYDRATER_TRANSCRIBE_MAX_MINUTES` 才切。

### M2b 一节课多个录音文件 ✔ 方案已确认

**目标**：一节课被录成多个文件（如上下半节）时一起整理；时间戳标明是第几个文件，例如 `2 - 11:23`。

**做法**：

1. **数据模型**：`Lecture.recording` 改为 `recordings: list`；时间点从"秒"改为"第几个文件 + 秒"（`domain/` 新增 `Moment`），所有带时间的模型（逐字稿分句、通知、笔记引用）随之调整。只有一个文件时显示与现在相同的 `11:23`，有多个文件时显示 `2 - 11:23`。
2. **编号说明**：有多个文件时，三份输出的开头都列出编号与文件的对应关系，例如"录音 1 = 上半节.mp4（52:10），录音 2 = 下半节.mp4（48:35）"。
3. **流水线**：每个文件单独提取音频、单独识别（各自缓存，增删一个文件不影响其他文件），再按顺序合并为一份逐字稿交给脱水。
4. **文件顺序**：录音的顺序就是上课的顺序，必须由用户决定，程序从不自行排序（不按文件名，也不按处理完成的先后）。
   - 命令行：严格按输入行中路径出现的先后；脚本形式按 `-i` 出现的先后。
   - 确认界面按顺序列出每个录音（编号、文件名、时长），顺序不对时可以输入新顺序（如 `2 1`）调整，而不必重新输入路径。
   - **【待确认】拖入终端时的顺序**：多选文件拖入终端后，路径的排列顺序由文件管理器和终端决定，可能是选中的先后，也可能是按文件名或其他规则。程序只能看到终端粘贴进来的文字，无法得知选中顺序。需要在 Dolphin、Nautilus、Finder、Windows 资源管理器上实测；若顺序不可靠，确认界面的调整功能就是兜底办法。
   - GUI（M7）中：按拖入时系统提供的顺序排列，并可拖动调整；同样不按处理完成的先后排序。
5. **输入**：交互式和 `process -i` 都接受多个音视频文件；确认界面列出每个文件的时长。
6. **兼容**：数据格式变化会让旧工作区的缓存失效。为避免重新转写，写一次性迁移：把旧的单文件产物转换成新格式（文件编号为 1），并在版本说明中写明。

**完成标准**：两个文件的课程笔记中时间显示为 `1 - …` / `2 - …`，与录音实际位置一致，开头有编号说明；单文件课程的输出与 v0.1 相同；火山上限确认后，超过上限的录音能完整识别。

## M3 兼容 OpenAI 接口的语音识别

**目标**：语音识别可以使用 OpenAI 官方 `whisper-1`、自建的 whisper.cpp 服务器，以及 Groq 等兼容服务。

**做法**：

1. 新增设置 `DEHYDRATER_TRANSCRIBE_API`：`volcengine`（默认）或 `openai`。`setup` 在录音文件识别这一项先询问它。
2. 新增 adapter `asr_openai_compat.py`：multipart 上传音频，`response_format=verbose_json`，读取分段的起止时间。URL 为完整端点，因此 whisper.cpp 默认的 `/inference` 和 OpenAI 的 `/v1/audio/transcriptions` 都可以直接填写。
3. `openai` 协议下 API Key 可以为空（自建服务通常不鉴权），`missing()` 与 `setup` 相应调整。
4. 上限：OpenAI 官方单次 25MB，由 adapter 声明，触发 M2a 的切段；自建服务默认不限，可用 M2a 的设置覆盖。
5. 只接受返回时间戳的服务；返回中没有分段时间时明确报错，而不是输出没有时间的逐字稿（`gpt-4o-transcribe` 这类模型不返回时间戳）。
6. 已知问题：Whisper 对中文偶尔输出繁体、静音段重复幻觉。先在你的 whisper.cpp 服务器上实测，再决定是否需要后处理。

**【待确认】（开始 M3 时再定）**：

- whisper.cpp 服务器的地址与启动参数（是否设置了 `--inference-path`、使用的模型和语言）
- whisper.cpp 的 `verbose_json` 返回格式是否与 OpenAI 一致（分段时间的字段名、单位），需用你的服务器实测
- 是否同时验证 OpenAI 官方与 Groq，还是只保证 whisper.cpp

**完成标准**：用你的 whisper.cpp 服务器完整处理一节课；`check` 能验证两种协议的连通性。

## M4 课件辅助识别

**目标**：利用课件里的专业术语提高语音识别对 `TLB`、`fork()`、"进程控制块"这类词的准确率。

**做法**：

1. 新阶段 `extract_glossary`：调用一次大模型（复用脱水任务的设置），从全部课件文字中提取术语表（中文术语、英文缩写、函数名等），上限几百个。用大模型而不是规则，是因为中文术语没有明显的形式特征。
2. 术语表交给语音识别：
   - 火山：`corpus.context` 中的热词（上限 5000 个）。v0.1 已经写好了这条请求路径，但从未真实发送过，需要实测确认格式。
   - OpenAI 兼容：`prompt` 参数（约 224 token），只放最重要的术语。
3. 术语表变化会让识别缓存失效（识别比较贵），因此术语表的生成要稳定：结果排序、去重，同一份课件得到同样的输出。
4. 没有课件时跳过，与现在相同。

**完成标准**：同一节课在开启与关闭辅助识别时各识别一次，人工对比术语的识别错误数，有明显改善才默认开启。

**【待确认】**：若改善不明显，是保留为可选功能还是放弃。

## M5 PPTX 课件

**目标**：课堂资料可以直接用 `.pptx`。

**做法**：

1. 用 LibreOffice 无界面模式把 PPTX 转成 PDF（`soffice --headless --convert-to pdf`），之后与 PDF 走同一流程，M1 的截图也随之可用。转换结果缓存在 `cache/` 中。
2. 没有安装 LibreOffice 时，明确提示安装方法；不提供只抽文字的降级方案，避免同一份课件因环境不同得到不同结果。
3. 可选：用 python-pptx 读取演讲者备注，作为大纲和撰写的补充上下文。

**【待确认】**：是否需要读取演讲者备注。

**完成标准**：同一份课件的 PPTX 和导出的 PDF 生成的笔记基本一致；Linux、macOS、Windows 上都能找到 LibreOffice。

## M6 CLI 功能与设计更新确认

**目标**：M1–M5 给命令行带来了新的输入和选项，在做 GUI 和 Nextcloud 插件之前，先和你一起重新审视命令行的功能与交互，定下来后 GUI 和插件照此设计。

**需要审视的内容**：

- 多个录音时的输入、排序与确认（M2b）
- 语音识别协议的选择与设置流程（M3）
- 课件辅助识别、截图等功能是否需要开关（M1、M4）
- PPTX 依赖缺失时的提示（M5）
- 整体交互是否仍然简洁，帮助信息和 README 是否需要重写

**同时完成**：把取消、进度事件、错误分类等目前散落在 CLI 中的逻辑收拢到 `service.py`，让 GUI 和 Nextcloud 插件能直接使用，并补充 service 层的测试。

**完成标准**：你确认 CLI 的功能与交互；service 接口稳定，GUI 和插件不需要依赖 `cli/` 中的任何代码。

## M7 轻量桌面 GUI

**目标**：不用命令行也能完成设置和整理。轻量、原生窗口，不使用浏览器或网页视图。

**选型：PySide6**（Qt Widgets）。体积约 100MB，已确认可接受。三平台一致，`QTextBrowser.setMarkdown` 可直接预览笔记。曾比较 Tkinter + tkinterdnd2（最轻但预览困难）、Toga（控件少）、Flet（内置 Flutter 引擎，不够轻量）。

**范围**：

- 设置页：与 `dehydrater setup` 相同的设置，带验证
- 整理页：拖入录音和课件（顺序见 M2b，可拖动调整）、填写课堂名称和输出目录、按步骤显示进度、显示用量统计
- 完成后：预览 `notes.md`，提供"打开文件夹""用默认编辑器打开"按钮；不在 GUI 内编辑 Markdown
- GUI 只调用 `service.py`，不包含任何整理逻辑
- 异步流水线与 Qt 事件循环的衔接：在后台线程运行，或使用 `qasync`，实现时再定

**【待确认】**：

- 启动方式：`dehydrater gui` 子命令，还是单独的 `dehydrater-gui` 命令（或两者都有）
- PySide6 作为可选依赖（如 `uv tool install 'dehydrater[gui]'`），还是默认安装
- NixOS 上需要在 `flake.nix` 中提供 Qt 运行库，需在你的 NixOS 上验证

**完成标准**：不打开终端，从设置到得到笔记的全流程可在 GUI 中完成；三平台可启动。

## M8 Nextcloud 插件（兼作会议转写）

**目标**：在 Nextcloud 中选中录音（和课件），直接生成整理结果并保存回 Nextcloud。同时希望稍作改动后能用于**会议转写**，替代飞书的会议纪要功能。

**会议转写带来的设计影响**：

- 会议没有课件，整理目标也不同：需要的是会议纪要、决议、待办事项（负责人、截止时间），而不是以课件为主线的笔记。
- 因此提示词和输出模板要能按"场景"切换：课堂（现有）与会议（新增）。流水线的前半段（提取音频、切段、语音识别、脱水）可以共用，后半段（大纲、撰写、模板）按场景选择。这个"场景"概念最好在 M6 时一并设计进命令行。
- 会议常有多人发言，纪要中通常需要区分发言人。火山录音文件识别支持说话人分离（`enable_speaker_info`），但 Whisper 系列一般不支持。

**建议形式**：基于 Nextcloud 官方的 AppAPI 做一个外部应用（ExApp），用 Python 框架 `nc_py_api` 编写：在文件右键菜单中提供"整理这节课 / 整理这次会议"，在服务端容器里运行 `service.py` 中的同一套流程，把结果写回所选目录，通过 Nextcloud 通知告知完成或失败；API Key 在 Nextcloud 的应用设置中配置。这样不需要编写 PHP 应用，整理逻辑与命令行完全共用。

**【待确认】（开始 M8 前必须明确）**：

- 你的 Nextcloud 版本，以及是否已启用 AppAPI 和 Docker 部署
- 形式：服务端插件（上面的方案），还是只让本机的 dehydrater 通过 WebDAV 读写 Nextcloud 上的文件（工作量小得多，但不能在 Nextcloud 里直接触发）
- 会议纪要的输出内容与格式：纪要、决议、待办分别需要哪些字段
- 是否需要区分发言人；若需要，语音识别只能用支持说话人分离的服务
- 会议转写是放在 v1 内，还是 v1 只做课堂场景的插件，会议场景留到之后

## 横向工作

- **数据格式变更的处理**：M2b 和 M4 会改变产物格式或缓存键。原则是尽量不让已有的转写结果失效；无法避免时提供迁移，并在版本说明中写明影响。
- **文档**：每个里程碑完成后更新 README 的用法、`.env.example` 的新设置、design.md 的架构和取舍。
- **测试**：每项功能都有单元测试；涉及交互的部分补伪终端测试；涉及外部服务的部分用模拟服务测试，并在里程碑结束时用真实课程验证一次。

## 不在 v1 范围

- 任何视频画面识别
- 课程级汇总（跨讲次的通知清单、日历导出）
- v2 的 Tauri 重写与移动端
