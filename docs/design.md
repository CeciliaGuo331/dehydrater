# dehydrater 设计

本文记录项目的定位、v0.1 的实际架构、关键设计取舍和后续路线，供开发时参考。v0.1 的功能与验证结论见 [v0.1.md](v0.1.md)，用法见 [README](../README.md)。

## 1. 定位与原则

**解决的问题**：有些课老师照着课件念、口癖多、节奏慢，听回放很费时间。dehydrater 把一节课的录音和课件整理成可以直接复习的笔记，并保留逐字稿和录音时间，需要时可以回听核对。

**原则**：

- **自备 API，不建服务器**：用户自己提供各服务的 API Key，数据从用户电脑直连服务商，项目本身没有服务端。
- **只用音频和 PDF，不识别视频画面**（v2 及以前）：录像只用来提取音轨，总结的依据只有语音转写的文字稿和 PDF 课件。
- **写两遍**：v0.1 ~ v1 用 Python 快速验证流程、提示词和数据格式；v2 再用 Tauri + Rust 重写成跨平台桌面和移动应用。
- **代码可读性优先**：分层清晰，类型完整，可测试；优先使用成熟的开源库。

## 2. 架构

### 2.1 分层

```text
cli → service → bootstrap → config → pipeline | adapters → ports → domain
```

| 层 | 职责 |
| --- | --- |
| `cli/` | 交互与显示：命令定义、交互式整理、设置向导、进度界面、日志配置 |
| `service.py` | 整理一节课的应用流程：检查输入、推断日期、准备工作区、运行、汇总用量。CLI 和将来的 UI 共用 |
| `bootstrap.py` | 组合根：读配置，构造 adapters，注入各阶段，组装流水线 |
| `config.py` | 各任务的接入地址、模型、API Key 及查找顺序 |
| `pipeline/` | 阶段、产物、缓存、调度、事件；只依赖 `ports` 和 `domain` |
| `adapters/` | 第三方库与外部服务：PyAV、PyMuPDF、豆包语音、OpenAI 兼容的大模型 |
| `ports.py` | 流水线对外部能力的接口：`AudioExtractor`、`SlideReader`、`Transcriber`、`ChatModel` |
| `domain/` | 数据模型与纯函数，不做 IO |

**规则**（import-linter 在 CI 中强制）：上层可以依赖下层，反之不行；`pipeline` 与 `adapters` 互不依赖；`domain`、`ports`、`pipeline` 不得 import `av`、`pymupdf`、`openai`、`httpx`。换服务商只需新增一个 adapter；测流水线时注入假 adapter。

**编码约定**：basedpyright strict；依赖一律通过构造函数注入，无全局状态；第三方库的类型不越出 adapter；提示词和输出模板写在 `.j2` 文件里，不写在 Python 字符串里。

### 2.2 流水线

```text
extract_audio ─► transcribe ─► render_raw
                     │
                     └─► dehydrate ─► render_dehydrated
                              │
ingest_slides ────────────────┴─► outline ─► write_notes ─► render_notes
```

每个阶段声明自己读写哪些产物（`pipeline/artifacts.py`），只能通过 `StageContext` 读写声明过的产物，以保证缓存键完整。Runner 按顺序执行，命中缓存的跳过，并通过事件（开始、进度、警告、完成、失败）向外汇报，流水线本身不知道谁在显示。

面向用户的"步骤"由若干阶段组成（`pipeline/steps.py`）：提取音频、读取课件、语音转写、逐字稿脱水、撰写笔记。进度显示、`--redo` 和用量统计都以步骤为单位。

### 2.3 数据与工作区

一节课一个输出目录：

```text
输出目录/
├── lecture.toml        # 课堂名称、日期、录音与课件路径（用户可编辑）
├── notes.md  dehydrated.md  raw.md
└── cache/
    ├── audio.mp3       # 提取的音频
    ├── dehydrater.log  # 这节课的整理日志
    ├── artifacts/      # 各阶段产物（JSON）
    ├── stages/         # 各阶段的缓存键、耗时、token 用量、录音时长
    └── <阶段名>/       # 阶段自己的中间文件：dehydrate/chunks、write_notes/chapters
```

主要的数据模型（pydantic，见 `domain/`）：

| 模型 | 内容 |
| --- | --- |
| `Lecture` | 标题、日期、录音和课件的路径（大小与修改时间参与缓存键） |
| `Transcript` | 分句列表（起止时间、文字）；原始稿一句一项，脱水稿一段一项 |
| `Deck` | 全部课件页：全局页码、所属文件、文件内页码、文字 |
| `Outline` | 概览、章节（课件页码范围、讲课段落范围）、术语、通知 |
| `LectureNotes` | 概览、章节（标题、课件位置、开始时间、Markdown 正文）、术语、通知 |

## 3. 关键设计取舍

| 决定 | 理由 | 放弃的做法 |
| --- | --- | --- |
| **时间戳从不由模型生成**：模型只引用句子、段落编号，程序换算成时间 | 模型会编造或算错时间；编号可以校验 | 让模型直接输出 `[mm:ss]` |
| **不使用视频画面**：录像只取音轨 | 文字稿加 PDF 已经足以把讲解对应到课件页（见下一条）；处理画面会显著增加复杂度和依赖 | 抽取关键帧与课件页做图像匹配来辅助对齐 |
| **由模型完成"讲解对齐到课件"**：大纲阶段一次读入全部课件和脱水稿来分章 | 能处理从课件中间开讲、跳讲、回翻、课件外插叙；实测效果好，代码量小 | 原计划用字符 n-gram 相似度 + Viterbi 求全局最优翻页序列。若将来要压低成本或模型对齐不准，可以作为备选 |
| **笔记分两步**：大纲一次调用，正文按章并发 | 一次写完整篇笔记容易写不完、越写越潦草 | 一次生成全文；先写各页再"全局组装"重写 |
| **脱水是精炼改写，而不只是删口癖** | 只删不改写只压到原文的 77%，仍然啰嗦；改写后约 25%，信息点完整 | 保留老师原话措辞 |
| **只为实际讲到的课件页建章**，每章必须对应讲课段落 | 一份课件通常讲好几节课 | 把整份课件都整理进笔记 |
| **两级缓存**：阶段级缓存键包含输入摘要、模型参数和提示词摘要；阶段内每次模型调用另有块级缓存，并保存当初的 token 用量 | 调提示词时不必重新转写；中断后只补缺失的部分；用量统计反映产出结果的完整成本 | 不缓存，或只缓存整个阶段 |
| **结构化输出**：JSON 模式 + pydantic 校验 + 业务校验（编号范围、顺序、覆盖率），不合格时把错误告诉模型，最多重试 3 次 | 模型偶尔输出非法 JSON 或越界编号 | 只靠提示词约束格式 |
| **配置按任务**：四个任务各有地址、模型、Key，环境变量 → `.env` → 用户配置目录 → 默认值 | 用户的心智模型就是"每个调用点一套设置"，也便于混用不同服务 | 渠道与任务两层配置；系统钥匙串（在没有桌面环境的 Linux 上不可用） |
| **语音识别用豆包录音文件识别标准版，base64 内联提交** | 中英混杂效果好、有毫秒级时间戳；官方文档只写了 URL 方式，但实测内联可用，免去对象存储 | 方舟多模态模型"听"音频（时间戳靠模型猜，会漏句）；极速版（未开通） |
| **语音识别开启 TCP keepalive 并自动重试** | 上传完后服务端一两分钟才响应，空闲连接可能被网络设备断开 | — |
| **方舟模型自动关闭深度思考** | 默认开启时一句话的回答要 40 秒、上千个推理 token，本项目的任务都不需要 | 让用户自己配置 `extra_body` |
| **音频统一转成 16kHz 单声道 MP3** | 各家服务普遍支持 | Opus 体积可减半，但需实测服务端是否接受 |
| **PyMuPDF 读课件，项目因此采用 AGPL** | 好用，作者对许可证没有偏好 | pypdfium2 |
| **自己写调度与缓存**（runner、stage、cache 三个文件共约 340 行） | 只有九个按顺序执行的阶段，引入 DAG 框架带来的概念比省下的代码多 | Hamilton、Prefect |
| **伪终端测试**：pexpect 运行真实的 `dehydrater` 命令，pyte 渲染屏幕后检查用户实际看到的内容 | 函数级测试抓不到终端里的问题，例如进度动画盖住提问 | 只用预设回答调用函数 |
| **日志写文件，界面只显示结论**：每节课一份，另有全局日志；记录 httpcore 的连接事件，不记录 API Key | 网络问题只有靠日志才能定位 | 只在终端打印 |

## 4. 路线图

### 近期（v0.x）

- **兼容 OpenAI 接口的语音识别**：OpenAI `whisper-1`、自建的 whisper.cpp 服务器、Groq 等，都使用 `/audio/transcriptions` 的 multipart 上传和 `verbose_json` 时间戳。需要新增一个"协议"设置；自建服务可以不填 Key；OpenAI 官方有 25MB 上限，长录音需要切段
- **长录音切段**：在静音处切开，分别识别后拼接时间戳；同时解决单次时长上限
- **版本号**：从 git 提交生成版本号，使 `--version` 和 `uv tool upgrade` 能区分不同提交
- **更小的上传体积**：实测豆包语音是否接受 ogg/opus，可把上传体积减半
- **课件图片**：把 PDF 中含图表的页渲染成图片嵌入笔记，或交给多模态模型读图（仅限 PDF 课件，不涉及视频画面）
- **课件辅助识别**：从课件抽取术语表作为语音识别热词；豆包录音文件识别 2.0 还支持把课件图片作为识别上下文
- **PPTX**：用 LibreOffice 转成 PDF 后走同一流程
- **段落重复归章**：大纲有时把同一段讲解归入两章，可以加校验

### 课程级功能

- **课程目录**：多节课放在同一个课程目录下，共享设置
- **通知汇总**：跨讲次汇总课堂通知，按类别（签到、考试、作业、调课、成绩）分组、按截止日期排序；保留原话和录音时间供核对（语音识别最容易听错数字和日期）；有明确日期的导出为日历文件；用户的"已处理"标记单独存放，重新生成时不丢失

### 图形界面

- 先在 v1 中用 NiceGUI（纯 Python、浏览器渲染）做一个轻量界面：拖拽上传、进度、Markdown 编辑与预览、点击 `▶ 时间` 跳转播放录音。整理流程直接复用 `service.py`
- 有编辑功能后需要区分"生成稿"和"用户稿"：重新生成时不覆盖用户改过的文件，而是另存并提示差异

### v2：重写

- Tauri 2（桌面三平台 + iOS/Android）+ Rust 核心，前端用 Svelte 或 Vue，Markdown 编辑器考虑 Vditor 或 Milkdown
- 直接复用：`.j2` 提示词（Rust 的 minijinja 语法兼容）、工作区与产物的数据格式、真实课程的评测样本
- 分发：Tauri 打包 msi / dmg / AppImage / deb，Arch 用 AUR，NixOS 用 flake

## 5. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 模型删过头或编造内容 | 笔记失真 | 脱水字数比例超出 15%–60% 时告警；出自讲解的内容都带录音时间，可以回听核对 |
| 通知中的日期、数字识别错误 | 错过截止时间 | 通知附带录音时间；课程级汇总时保留原话 |
| 依赖单一服务商 | 服务变动或涨价时不可用 | 大模型已兼容 OpenAI 接口；语音识别计划增加兼容 OpenAI 接口的实现 |
| 课程录像的版权 | 分享产物可能不合规 | 工具纯本地运行、不托管任何内容；产物仅供个人学习 |
