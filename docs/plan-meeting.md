# 会议纪要计划

在 v1 的 M7（桌面 GUI）完成后，从 `dev` 分出 `meeting` 分支开发。目标是让 dehydrater 除了整理课堂，也能把**带 PPT 的会议**整理成纪要，替代飞书的会议纪要功能。v1 计划见 [plan-v1.md](plan-v1.md)，架构见 [design.md](design.md)。尚未确认的问题标为 **【待确认】**，汇总在文末。

## 1. 为什么做

组会汇报、学术报告、项目评审、答辩这类会议都有 PPT。对它们来说，dehydrater 的核心能力正好适用，而现成工具做不到：

| | 现成工具（Speakr、Scriberr、Nextcloud Assistant 等） | dehydrater |
| --- | --- | --- |
| 转写与总结 | ✅ | ✅ |
| 按 PPT 结构组织纪要，每页对应讲解 | ❌ 只基于转写文字总结 | ✅ 已有：大纲、对齐、按章撰写 |
| 讲者从中间页开讲、跳页、回翻 | ❌ | ✅ 已在真实课程上验证 |
| PPT 截图嵌入纪要 | ❌ | v1 的 M1、M5 完成后可用 |
| 区分发言人 | ✅ 部分支持 | ❌ 本计划补上 |
| 决议与待办 | ✅ 部分支持 | 有雏形：课堂场景已从讲话中抽取"通知"这类事务性内容 |

没有 PPT 的纯讨论会，dehydrater 仍可用"无课件"模式（按讲话内容分章），但现成工具在这类场景已经足够，不是本计划的重点。

**现成工具的情况**（来自项目介绍和第三方评测，未实际部署验证）：

- **Speakr**：自托管 Web 应用，AGPL-3.0。语音识别和大模型都走兼容 OpenAI 的接口；说话人分离需要自建 WhisperX 后端（本地模型）或 OpenAI 的 `gpt-4o-transcribe-diarize`
- **Scriberr**：自托管，MIT，本地运行 Whisper 系列模型，支持离线说话人分离，总结可接 OpenAI 接口
- **Meetily**：桌面端，本地 Whisper 加 Ollama
- **Nextcloud**：Talk 有实时转写（基于 Vosk）；Assistant 能为录制的通话生成转写并总结

## 2. 与课堂场景的差异

流水线完全相同：提取音频 → 转写 → 脱水 → 大纲 → 撰写 → 渲染。不同之处只有三点，设计目标是**加内容、不加分支**。

### 2.1 提示词与模板按场景区分

- 课堂强调知识点、老师的补充讲解、考点；会议强调议题、各方观点、讨论结论。
- 按场景放两套 `.j2` 文件，例如 `prompts/lecture/`、`prompts/meeting/`，以及对应的输出模板。阶段代码不区分场景，只由组合根按场景选择模板目录。
- 场景计入缓存键：同一份录音切换场景时，大纲和撰写会重做，转写和脱水不受影响。
- **【待确认】脱水是否也要按场景区分**：课堂脱水会把对话改写成"学生问 / 老师答"，会议需要保留多人讨论的结构。

### 2.2 事务性内容：决议与待办

- 课堂抽取"通知"；会议抽取"决议"和"待办"。
- 把现有的 `Notice` 扩展为通用的"事项"：类型（通知、决议、待办）、内容、录音时间，以及可选的负责人和截止时间。
- 截止时间多为相对说法（"下周三前"），需要结合会议日期换算；换算结果与原话同时保留，供核对。

### 2.3 区分发言人

- 火山录音文件识别支持说话人分离（`enable_speaker_info`，分离版本 `ssd_version`）。逐字稿每句增加可选的说话人标签，脱水和撰写时保留。
- 识别结果是"说话人 1、说话人 2"。要换成真实姓名，需要用户在整理后提供对应关系，程序重新渲染（不必重新识别）。
- Whisper 系列（包括 v1 M3 接入的 whisper.cpp）一般不支持说话人分离，使用它们时纪要中没有发言人信息。
- **【待确认】是否需要区分发言人**。若需要，会议场景只能用火山识别。

## 3. 里程碑

| 里程碑 | 内容 | 完成标准 |
| --- | --- | --- |
| **G1** 场景框架 | 场景概念、按场景选择提示词与模板、CLI 与 GUI 中的场景选择 | 课堂场景的输出与之前完全一致 |
| **G2** 会议提示词与模板 | 会议的大纲、撰写提示词，纪要模板 | 一场带 PPT 的真实会议生成可用的纪要 |
| **G3** 决议与待办 | 通用"事项"模型、抽取、截止时间换算 | 待办带负责人和截止时间，可回听核对 |
| **G4** 发言人 | 火山说话人分离、逐字稿与纪要中的发言人、姓名对应 | 纪要中发言归属正确；改姓名只需重新渲染 |

G1 完成后，v1 的 M8（Nextcloud 插件）可以直接同时支持课堂和会议。

## 4. 对 v1 的影响

v1 不实现会议场景，也不为它提前写代码。仅有一点值得在 v1 中注意：

- **【待确认】M6 设计 CLI 时，是否给"场景选择"预留位置**（例如交互流程中的一个提问、`process` 的一个选项），以免会议分支合入时再改一次交互。

## 5. 待确认事项汇总

| 问题 | 何时确认 |
| --- | --- |
| 是否需要区分发言人（若需要，会议场景只能用火山识别） | 开始 G4 前，最好在开分支时 |
| 纪要包含哪些部分（议题、各方观点、决议、待办……）及格式 | 开始 G2 前 |
| 待办需要哪些字段（负责人、截止时间、其他） | 开始 G3 前 |
| 脱水是否也要按场景区分 | 开始 G1 时 |
| 会议录音通常来自哪里（Nextcloud Talk 录制、其他会议软件导出、手机录音），决定插件的接入方式 | 开始 v1 M8 前 |
| v1 的 M6 是否给场景选择预留位置 | 开始 v1 M6 时 |
| Nextcloud Talk 自带的转写与总结对中文会议的效果，作为对照 | 任意时间，可用来判断本计划的必要性 |
